  C'est quoi un Dockerfile, en vrai ?

  Imagine une recette de cuisine. Le Dockerfile, c'est la liste d'instructions
  écrites à l'avance : "prends cette base, ajoute ça, puis ça, puis fais cuire
  comme ça". Docker lit cette liste et fabrique une image — un genre de boîte
  figée qui contient ton appli et tout ce qu'il lui faut pour tourner (Node.js,
  tes fichiers, les dépendances).

  Ensuite, quand tu lances cette image, ça devient un conteneur — c'est le plat
  une fois sorti du four, en train de tourner réellement.

  Résumé : Dockerfile (recette) → image (la chose construite) → conteneur
  (l'image en train de tourner).

  Pourquoi ton backend en a besoin

  Ton backend, c'est du code Node.js/NestJS. Pour qu'il tourne, il faut :
  1. Un endroit avec Node.js installé
  2. Installer les dépendances du projet (le npm ci, qui lit package.json)
  3. Démarrer le serveur

  Le Dockerfile, c'est juste ça écrit sous forme de recette, étape par étape.

  Les 4 lignes de base que tu vas devoir écrire (en gros, sans détail technique
  pour l'instant) :

  1. "Pars de cette image Node.js" (une base toute prête, comme une pâte à tarte
     déjà faite)
  2. "Copie les fichiers du projet dans la boîte"
  3. "Installe les dépendances" (npm ci)
  4. "Quand on démarre le conteneur, lance le serveur"

  C'est tout, pour un premier jet. Pas besoin de penser tout de suite à
  l'optimisation, au cache, au multi-stage — j'irai trop vite si je remets ça
  maintenant.

  Un concept à connaître avant d'écrire ton Dockerfile : ENTRYPOINT vs CMD

  Dans un Dockerfile, il y a deux instructions qui définissent "que fait le
  conteneur quand il démarre" :
  - ENTRYPOINT : le programme/script qui démarre toujours, en premier.
  - CMD : des arguments par défaut, qu'on peut envoyer à l'ENTRYPOINT.

  Concrètement pour toi : ENTRYPOINT pointera vers ton entrypoint.sh, et ce
  script, à la fin, lancera le vrai serveur. Pas besoin d'utiliser CMD du tout
  si ton script fait tout lui-même.

  Ce que ton entrypoint.sh doit contenir, en 3 étapes simples (en langage
  naturel, pas encore en code) :

  1. Tout en haut : une ligne spéciale qui dit "ce fichier s'exécute avec le
     shell sh" (la première ligne d'un script shell, appelée le shebang).
  2. Une instruction qui dit "arrête le script immédiatement si une commande
     échoue" — c'est ce qui garantit que si la migration plante, on ne continue
     pas.
  3. Ensuite, dans l'ordre : lancer prisma migrate deploy, puis lancer le
     serveur (node dist/main.js ou équivalent, à voir avec ce que Léo mettra en
     place).

  Petite question avant que tu écrives ça : est-ce que tu sais déjà quelle
  commande démarre concrètement le serveur NestJS une fois compilé (node
